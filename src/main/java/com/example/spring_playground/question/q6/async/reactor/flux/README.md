# Flux로 여러 주문 전달하기

- 입문 예제: [FluxBaseMain](./FluxBaseMain.java)
- 완료·오류·취소: [FluxLifecycleMain](./FluxLifecycleMain.java)

[FluxBaseMain](./FluxBaseMain.java)의 main()을 IDE에서 실행한다. 별도 서버는 필요 없다. 공통 주문 1·2·3번을 모두 사용한다.

- `Flux.fromIterable()`: 목록의 각 주문을 전달하는 흐름을 구성한다. 목록 조회는 구성 시 실행되지만, 주문 전달과 제작은 아직 실행하지 않는다.
- `subscribe()`의 첫 번째 함수: 주문 하나를 받을 때마다 실행한다. 이 예제에서는 받은 주문을 접수하고 제작한다.
- 두 번째 함수: 오류를 처리한다.
- 세 번째 함수: 전체 흐름이 정상 완료됐을 때 한 번 실행한다.

로그 흐름은 A 구성 → B 구독 → 주문별 전달·제작·알림 → 전체 완료 → subscribe() 반환 순서로 확인한다. B 부분을 주석 처리하면 구성만 한 경우를 확인할 수 있다.

별도 스케줄러 없이 main 스레드에서 순서대로 제작한다. Flux가 여러 값을 전달한다고 자동으로 비동기나 병렬 실행이 되는 것은 아니다. 이번 예제는 유한한 목록을 사용하므로 전체 완료 신호가 있지만, 계속 메시지를 수신하는 Flux는 연결이 유지되는 동안 완료되지 않을 수도 있다.

실행 확인: 로컬 JDK 21과 캐시의 Reactor Core 3.8.7로 직접 컴파일·실행했다. 구성 시에는 제작 로그가 없었고, 구독 후 주문 1·2·3의 전달·제작·알림이 순서대로 실행됐다. 전체 완료 함수는 한 번 호출됐으며 마지막에 subscribe() 반환 로그가 출력됐다. 모두 main 스레드였다.

## 완료·오류·취소 실험

FluxLifecycleMain.main()을 실행하면 정상·오류·취소 상황을 순서대로 확인한다. 이 예제에서는 map()으로 주문을 제작 완료 문자열로 변환한다. 입문 예제의 Flux<Order>와 달리 제작 결과를 전달하는 Flux<String>이다.

| 상황 | 확인할 흐름 |
| --- | --- |
| 정상 | 1·2·3번 결과 onNext → onComplete → doFinally(onComplete) |
| 오류 | 1번 결과 → 2번에서 의도적인 실패 → onError → doFinally(onError) |
| 취소 | 1번 결과 → cancel → doFinally(cancel) |

오류 시 3번은 제작되지 않고 정상 완료 함수도 호출되지 않는다. 취소 시 2·3번은 제작되지 않으며 완료·오류 함수도 호출되지 않는다. 취소 타이밍을 직접 지정하려고 취소 예제에서만 BaseSubscriber를 사용한다. 첫 결과를 받는 hookOnNext()에서 cancel()을 호출하는 부분에 집중한다.

이미 제작한 1번은 취소해도 되돌아가지 않는다. 별도 스케줄러 없는 순차 흐름에서의 관찰이며, 모든 외부 작업의 즉시 중단을 보장하는 의미는 아니다.

실행 확인: JDK 21과 Reactor Core 3.8.7로 직접 컴파일·실행하여 표의 신호를 확인했다. 오류 상황에서는 3번 제작과 정상 완료 로그가 없었고, 취소 상황에서는 2·3번 제작과 완료·오류 로그가 없었다.
